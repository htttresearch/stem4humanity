# Storage design: canonical store + registry + DuckDB query layer (Design A)

Date: 2026-08-05. Status: implemented (see `algofinder/store/`).

## Decision

Three-tier discipline, no duplication of source data:

1. **Canonical store** (system of record, immutable): the existing
   `public/` artifact files — instance manifests, benchmark run records,
   reference registry + snapshots — plus `private/sessions/` traces.
   Nothing derived is ever written back into these files.
2. **Registry** (`private/registry/*.jsonl`, append-only, digest-checked):
   an inventory of what exists — instances, solvers, runs, environments —
   with metadata and content digests. Regenerated by the indexer in sorted
   order, so a rerun produces byte-identical logs (effectively append-only).
3. **Query layer** (`private/db/analytics.duckdb`, gitignored): DuckDB
   **views over the canonical files** (read_json_auto, zero-copy) plus
   regenerable Parquet caches for hot tables. The DB never owns data; it
   references canonical bytes and caches derived projections.

Rationale (full tradeoff study vs a registry-only canonical store): single
system of record; every displayed number traces to a content-addressed
artifact; multi-process pipeline needs no DB locks (DuckDB is single-writer);
no export step for publishing (files are git-committable as today);
append-only discipline is structural, not policy.

## Layout

```
public/data/*_manifests.json        canonical instances
public/results/benchmark.json       canonical run records
public/data/references/registry.jsonl, references_snapshot.json   canonical references
private/sessions/…                  canonical dev-mode traces
private/registry/{instances,solvers,runs,environments}.jsonl      registry (indexer-owned)
private/db/analytics.duckdb         query layer (gitignored)
private/db/cache/*.parquet          materialized caches (gitignored, regenerable)
```

## Registry entries

`{kind, id, digest, source, schema_version, fields…}` — digest is sha256 of
the canonical byte/file content. `verify()` recomputes digests from the
canonical files and reports mismatches; `rebuild()` rescans deterministically.

## DuckDB views

- `v_instances` — over `public/data/*_manifests.json`
- `v_runs` — over the configured results glob (default `public/results/*.json`)
- `v_references` — over the reference registry JSONL
- `v_solvers`, `v_environments` — over registry JSONL
- `v_features` — reserved for phase 6 feature vectors

Parquet caches: `runs.parquet`, `instances.parquet` (zstd, row groups ~100k).

## Parity gate

`index --parity` compares SQL-derived leaderboard rows against
`algofinder.harness.leaderboard.summarize()` over the same runs: exact
status counts, float-tolerance mean gap/wall, identical best_on/exact.
Mismatch → nonzero exit. This is the acceptance test for the layer
(no code tests per repo rules; the real pipeline is the test).
